# 견적서 프로그램 (원본 `.xls` 양식 보존 방식)

원본 `template/견적서.xls` 의 **OLE2 컨테이너와 BIFF8 레코드를 그대로 유지**한 채
사용자가 입력한 셀 값만 교체해서 새 `.xls` 를 만든다.
새 파일을 만들지 않고, 라이브러리로 재생성하지도 않는다. → **경로 A 채택, 경로 B 불필요**

---

## 0. 준비 — 원본 양식 넣기

**저장소에는 원본 `.xls` 양식이 들어 있지 않습니다.** 법인 직인 이미지·사업자등록번호·
계좌번호가 들어 있어 제외했습니다. 아래 위치에 본인 양식을 두어야 동작합니다.

```
template/견적서.xls
```

요구 조건과 다른 양식을 쓰는 방법은 `template/README.md` 를 보세요.

## 1. 실행

```
start.bat              (또는)  python backend\server.py
```

브라우저가 자동으로 열린다. 필요한 것은 **파이썬 3.8 이상뿐**이고,
외부 패키지는 하나도 쓰지 않는다 (표준 라이브러리만). 테스트에만 `xlrd` 를 쓴다.

```
python tests\run_all.py        전체 검증 실행
```

## 2. 구조

```
quote-app/
├─ template/견적서.xls      원본. 프로그램이 절대 수정하지 않는다 (읽기 전용)
├─ config/mapping.json      셀 매핑 (BIFF 분석으로 확정한 실제 주소, 추측값 없음)
├─ backend/
│   ├─ xlsbiff.py           ★ 핵심: OLE2(CFB) 읽기/쓰기 + BIFF8 레코드 편집 엔진
│   ├─ quote_writer.py      매핑 적용, 계산, 견적서 생성
│   └─ server.py            로컬 HTTP 서버 (표준 라이브러리)
├─ web/                     UI (index.html / app.js / style.css)
├─ tests/                   검증 4종
└─ out/                     생성 결과 사본
```

## 3. 왜 원본 `.xls` 직접 수정이 가능했나

`xlutils`/`xlwt` 계열은 파일을 **재생성**하므로 이미지(Escher/MSODRAWING)와 상당수 서식이
소실된다. 그래서 쓰지 않고, 다음을 직접 구현했다.

* **OLE2/CFB 컨테이너**: 디렉터리 엔트리를 원본 바이트 그대로 복사하고
  start-sector/size 필드만 갱신. 헤더·FAT·DIFAT 재구성.
* **BIFF 레코드 편집**: 레코드 목록을 그대로 보존한 채 대상 셀 레코드만 교체.
  빈 셀은 `MULBLANK` 를 분할해 끼워 넣고, **원래 그 칸에 걸려 있던 XF(서식) 인덱스를 승계**한다.
* **오프셋 의존 레코드 재계산**: 레코드가 밀리면 깨지는 4가지를 원본 규칙 그대로 재생성.
  `BOUNDSHEET.lbPlyPos` / `INDEX.rgibRw` / `DBCELL.dbRtrw·rgdb` / `EXTSST.ib·cbOffset`
  — 규칙은 추측하지 않고 원본 파일에서 실측해서 역산했다.

정당성 증거: **아무것도 고치지 않고 다시 쓰면 원본과 79,360 바이트 전부가 동일**하다
(`tests/test_roundtrip.py`). 즉 파서·직렬화기·오프셋 재계산이 Excel 과 같은 결과를 낸다.

## 4. 확정된 셀 매핑 (BIFF 분석 결과)

| 항목 | 셀 | 원본 서식 |
|---|---|---|
| 발행일자(견적일자) | `C12` (병합 C12:D12) | xf135, 날짜서식 `yyyy"년" m"월" d"일"` → 숫자(일련번호)로 기록 |
| 발행번호(견적번호) | `C13` | xf83 |
| 공급처(거래처명) | `C14` | xf88 |
| 담당자 | `D14` | xf87 · **원본에 전용 라벨 없음** (공급처 우측 빈 칸) |
| 품명(건명) | `C15` | xf88 |
| 금액 | `C16` | xf99, 통화서식 → `=H62` 수식 |
| 유효기간 / 납기 / 결재조건 / 은행계좌 / 특이사항 | `C17`/`C18`/`C19`/`C20`/`C21` | |

품목 영역 **23행 ~ 58행 (최대 36행)**

| 열 | 항목 | 적용 XF (원본에 이미 있는 서식) |
|---|---|---|
| B | 번호 | 113 · Times New Roman 9pt 우측 |
| C | 품명 | 109 · TNR 9pt 좌측 |
| D | 규격 | 111 · TNR 9pt 가운데 |
| E | 단위 | 98 · 바탕 10pt 가운데 |
| F | 수량 | 116 · 바탕 10pt 가운데 |
| G | 단가 | 118 · TNR 10pt 우측, `"₩"#,##0` |
| H | 금액 | 118, 수식 `=F{행}*G{행}` |

합계 영역

| 항목 | 셀 | 처리 |
|---|---|---|
| 공 급 가 | `H60` | `=SUM(H23:H58)` 로 교체 (아래 5-④ 참조) |

| 합　　계 | `H62` | **원본 수식 `=H60+H61` 레코드를 바이트 그대로 유지**, 결과 캐시값만 갱신 |

## 5. 원본과 달라지는 점 (전부 의도된 4가지, 그 외에는 없음)

1. **품목 영역(23~58행)의 기존 샘플 데이터가 지워진다** — 새 견적서이므로 당연.
   값이 들어 있던 셀만 비우고, 원래부터 비어 있던 셀의 레코드는 건드리지 않는다.
   상단 정보칸도 마찬가지로, **입력하지 않은 항목은 비운다.** 예를 들어 품명을 비워두면
   원본 `C15` 의 예전 내용(`부속케이블 60kW (2세트:Sourse+Bias)`)이 남지 않고 빈 칸이 된다.
   단, `config/mapping.json` 의 `defaults` 에 값이 있는 항목(유효기간·납기·결재조건·은행계좌)은
   비워두면 그 기본값이 들어간다.
2. **품목 행의 서식이 열 단위로 통일된다** — 원본 23~58행은 그룹 제목행(굵게·큰 글씨)과
   일반 품목행이 섞여 있어서, 일반 품목을 그대로 채우면 5번째 품목만 굵게 나오는 식이 된다.
   위 표의 XF 로 통일한다. **새 서식을 만들지 않고 원본에 이미 있는 XF 인덱스만 재사용**하므로
   XF/FONT/FORMAT 레코드는 137/53/26개 전부 원본과 바이트 동일하다.
3. **품목 영역 행 높이를 195(9.75pt)로 통일** — 원본 26행은 높이가 120(6pt)인 얇은 구분선용
   행이라 여기에 품목이 들어가면 글자가 잘린다. 23·24·25·26·27·42·43행 7개만 바뀌고
   (36행 중 29행은 원래부터 195), 품목 영역 밖의 행 높이는 전혀 건드리지 않는다.
   높이를 지정하면서 `fUnsynced` 플래그를 켠다(Excel 이 높이를 자동으로 되돌리지 않게 하는 표준 플래그).
4. **`H60` 공급가액 수식 교체** — 원본은 `=H27+H43` 으로, 예전 문서의 그룹 소계 2칸만 더하는
   구조다. 품목을 순서대로 채우면 27·43행은 그냥 5번째·21번째 품목이 되어 합계가 틀린다.
   그래서 `=SUM(H23:H58)` 로 바꾼다. `config/mapping.json` 의 `totals.supply.mode` 를
   `"keep"` 으로 두면 원본 수식을 그대로 둘 수도 있다.
   **부가세·합계 수식은 손대지 않는다.**

## 6. 검증 결과 (`python tests\run_all.py` → 4/4 PASS)

| 요구 항목 | 결과 |
|---|---|
| 1. 정상적으로 열리는가 | 자체 BIFF 파서 + 제3자 `xlrd` 양쪽에서 열림 |
| 2. 회사 로고 유지 | JPEG 바이트 SHA-256 동일 |
| 3. 법인 직인 유지 | JPEG 바이트 SHA-256 동일 |
| 4. 셀 서식 유지 | XF 137 / FONT 53 / FORMAT 26 / STYLE 49 / XFEXT 55 / STYLEEXT 49 전부 바이트 동일 |
| 5. 병합 셀 유지 | `MERGEDCELLS` 레코드 동일, 4건 확인 |
| 6. 테두리 유지 | 테두리는 XF 레코드에 들어 있음 → 4번과 동일 근거 |
| 7. 인쇄 레이아웃 유지 | SETUP/PLS/HEADER/FOOTER/여백4/HCENTER/VCENTER/COLINFO/DEFCOLWIDTH/DEFAULTROWHEIGHT/WSBOOL/HEADERFOOTER 전부 동일 |
| 8. 데이터 위치 정확성 | `xlrd` 로 C12~C21, B23~H58, H60~H62 전수 확인 |
| 9. 기존 수식 유지 | `H61`·`H62` rgce 바이트 동일 |
| 10. 양식 차이 없음 | 91종 레코드 중 79종 완전 동일. 나머지는 5장에 적은 셀 값/행 높이 변경분뿐 |

추가로 확인한 것

* `MSODRAWINGGROUP`/`MSODRAWING`/`OBJ` 레코드 바이트 동일 → 이미지 위치·크기까지 보존
* `BOUNDSHEET`/`INDEX`/`DBCELL`/`EXTSST` 포인터가 전부 실제 레코드 경계에 안착
  (같은 검사를 Excel 이 만든 원본에도 돌려서 검사기 자체의 정당성을 먼저 보였다)
* 36행 × 긴 한글 문자열 → SST 9,339바이트로 레코드 한도 초과 → CONTINUE 분할 경로 정상
* 수량 0 / 소수 / 9억대 금액 / 특수문자(`①②③ ㈜·㎡`) / 빈 규격·단위 정상
* 같은 입력 → 같은 바이트 (결정적 출력), 연속 생성 시 상태 누적 없음, **원본 파일 SHA-256 무변경**

## 7. 남은 제약

* 품목은 **최대 36행**. 원본 양식의 품목 영역이 23~58행이고, 행을 늘리면 인쇄 1페이지 레이아웃이
  깨지므로 늘리지 않았다.
* 원본 양식에 **주소 전용 칸이 없다.** 별도 주소 입력란을 두지 않고, 필요하면 특이사항(`C21`)에
  직접 적는다. 주소를 따로 입력받아 특이사항 앞에 자동으로 붙이고 싶으면
  `config/mapping.json` 의 `address.mode` 를 `"remark"` 로 바꾸면 된다.
* 부가세율을 0.1 이외로 바꾸면 `H61` 수식을 `=H60*<비율>` 로 다시 쓴다(원본 수식 유지 불가).
* **최종 육안 확인은 Excel 에서 직접 열어보는 것으로 마무리해야 한다.** Office 인증 모달 때문에
  이 환경에서 Excel COM 을 띄울 수 없어, 대신 위와 같이 바이트/레코드/포인터 수준으로 검증했다.
  `out\` 폴더의 생성 파일을 열어 원본과 나란히 비교해 보면 된다.
